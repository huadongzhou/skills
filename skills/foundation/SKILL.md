# foundation — 项目四文档基建

为项目准备稳定的根级上下文文档，让任意代码助手进入项目即拥有一致的认知基础。

## 管辖范围（硬约束）

- 管理的项目文档只有四份，且只位于**仓库根目录**：`AGENTS.md`、`DESIGN.md`、`TODO.md`、`DMS.md`。
- 除下一条的例外外，其余任何文档（README.md、CLAUDE.md、docs/ 等）不属于本技能：不创建、不修改、不迁移，仅允许作为「解读项目」时的只读信息来源。
- **唯一例外**：仓库内 `templates/<四份名>.md` 是本技能的工作产物（同步的写入目标），不受上一条「不创建」约束；除此之外不得创建任何新文件。

## 两个 templates/：读哪里、写哪里

| 位置 | 角色 |
|---|---|
| 技能自带的 `templates/<名>.md` | **只读兜底基准**。仓库内无同名模板时读它。技能安装目录只读，任何情况下都不得写入。 |
| 仓库内的 `templates/<名>.md` | **同步的写入目标**，也是初始化/更新的**优先基准**（同步产物优先）。仓库里没有时，先从技能自带模板复制出同名文件，再写回。 |

**读取优先级（唯一规则）**：`<仓库根>/templates/<名>.md` 存在就用它，不存在才用技能自带的同名模板。这条让「同步」的反哺成果能回流到后续的初始化与更新，闭环成立。

## 文档定位

| 文档 | 是什么 | 解读项目时的主要来源 |
|---|---|---|
| AGENTS.md | 默认上下文 | package.json、构建/lint 配置、源码目录树、README |
| DESIGN.md | 设计上下文 | 设计稿、demo HTML、主题样式与令牌文件 |
| TODO.md | 待办账本 | 需求输入、issue、源码 TODO 注释、git log |
| DMS.md | 文档管理规范 | 现有目录结构、既有文档的命名与存放位置、git log |

上表只给主要来源；每份文档的完整章节结构与挖空点，以模板正文为准。

## 模板机制

`templates/<名>.md` = 公共结构与公共内容（跨项目通用，原样保留） + 挖空点。挖空点有三种形态，等价对待：

1. `<!-- 生成提示：... -->` 注释；
2. `{{占位符}}`；
3. 以正文自述「属挖空点／格式示范」的块（如 `templates/TODO.md` 的格式示范块）。

整套机制是完形填空：**初始化/更新 = 填空**（按项目事实填每个挖空点），**同步 = 挖空**（把项目文档长出的结构剜去项目特性、还原成挖空点写回模板）。

填空规则：

1. 公共内容原样带入；
2. 逐个挖空点按生成提示解读项目、产出内容，随后删除提示注释与未使用的占位；
3. 解读不到、无法验证的内容写「待补充：<缺什么、去哪找>」，不编造、不推定；「禁止依赖方向」这类规则性结论尤其如此，无代码依据时一律待补充；
4. 某节确无内容可填时，按该节的生成提示处置：提示要求删除整节的，删除该节；否则删除该节内的示例、格式块与悬空结构（空表头等），只留一行「待补充：<缺什么、去哪找>」；
5. 生成提示与上述规则冲突时，以上述规则为准；生成提示本身也是挖空点，用完即删，不得反过来改变规则。

## 操作一：初始化

场景：仓库根目录缺少一份或多份模板同名文档。对每份待生成文档独立执行：

1. 按「读取优先级」取基准模板（**输入**：基准模板 + 项目现状）；
2. 按「文档定位」表的来源解读项目；全新项目信息不足时，以用户的需求描述为解读对象；
3. **🔴 CHECKPOINT · 🛑 STOP**：先把将创建的文件路径清单交用户确认，确认后再落盘；跳过条件（唯一）为本次请求原话含免确认词（「直接生成」「直接写」「不用问我」「不用确认」等），跳过时须在回复首行引用该原话；
4. 生成 `<仓库根>/<名>.md`（**输出**：新文档）；
5. 已存在的同名文档保持不动，在结果中提示可改走「更新」；
6. 按「执行纪律」的统一格式汇报。

**完成判据**：被处理的每份文档各有产出，其余每份各有一条跳过理由（「未点名」也算一条）；已存在的同名文档字节未变，并在汇报中给出核验输出。

## 操作二：更新

场景：仓库根目录已存在模板同名文档，需跟上项目现状。

1. 逐份重新读取文档现状与基准模板（**输入**：文档 + 基准模板）；
2. 逐章节对照，每个章节给出四选一处置（**输出**：处置清单）；
3. **🔴 CHECKPOINT · 🛑 STOP**：先把「将改动的章节清单 + 处置」交用户确认，确认后再落盘；跳过条件与操作一相同（原话含免确认词），跳过时须在回复首行引用该原话；
4. 以最小变更落笔（**输出**：更新后的文档）。

更新规则：

- 每个章节的四选一处置：**补齐**（模板有而文档缺，按生成提示填空）／**修正**（与项目现状冲突的事实：命令、目录、依赖、令牌值，核实后改）／**保留**（文档有而模板没有的章节，它是「同步」的输入）／**无变化**；
- 保持既有章节顺序与行文风格；人工补充与项目特性内容一律保留；
- **完成判据**：本次点名的每份文档，其每个章节都有一条处置，并在汇报中按章节列出处置与依据；标「无变化」须写出与基准模板的逐条对照结果（如「模板 18 个挖空点均已填」，数量须与该文档实际挖空点一致），仅凭印象标注不算。漏一个章节即未完成。

## 操作三：同步（反哺模板）

场景：项目文档演化出了基准模板中不存在的标题或内容结构。

1. 逐文档对比 `<仓库根>/<名>.md` 与基准模板（**输入**：文档 + 基准模板）；
2. 提取模板缺少的标题与表头，逐条给出处置：反哺／问用户／不适用（**输出**：反哺候选清单）；
3. **🔴 CHECKPOINT · 🛑 STOP**：把候选清单交用户确认，确认后再写入 `<仓库根>/templates/<名>.md`；跳过条件与操作一相同（原话含免确认词），跳过时须在回复首行引用该原话；
4. 标题原样追加、具体内容改写为生成提示后追加进模板（**输出**：更新后的仓库内模板）。

同步规则：

- 反哺范围：只反哺「结构」（标题、表头、组织方式）与跨项目通用的规则；
- 结构与内容的判定：标题（`#`/`##`/`###` 行）与表头一律原样反哺，不得自行改名、概括或翻译；段落正文、命令、路径、令牌、数值、日期一律视为项目值，还原成挖空点（改写为 `<!-- 生成提示：... -->`）；
- **对冲措辞不反哺**：标题或表头里的括注与限定语（「建议」「依据…推断」「待核实」等）是填空时的对冲措辞，属项目值，反哺时剔除；
- 「拿不准」的判据与处置：标题或表头含项目专名（产品名、内部系统名、团队名）时即为拿不准。**🔴 CHECKPOINT**：列出候选问用户，不默默写入；
- 方向单一：项目文档 → 模板；同步过程永不反向删改项目文档。

**完成判据**：项目文档中每个模板没有的标题与表头，都有一条处置（反哺 / 问用户 / 不适用），漏一个即未完成；项目文档本身零改动，并在汇报中给出核验输出。

## 异常与兜底

流程假设环境理想，实操常遇下列异常。命中即按表执行，绝不静默跳过。

| 触发条件 | 一线修复 | 仍失败兜底 |
|---|---|---|
| 技能自带模板文件缺失 | 跳过该份文档的处理，在汇报中说明缺失文件名 | 停止全部操作，请用户确认模板来源后重试 |
| 仓库根目录不可写 | 报告权限问题并列出待写入的完整路径 | 将待写入内容原样输出到对话，由用户自行落盘 |
| 同步目标 `templates/` 不存在 | 先从技能自带模板复制出同名文件，再写回 | 复制失败则跳过同步并汇报，不改项目文档 |
| 用户点名管辖范围外的文档（README.md、CLAUDE.md、docs/ 等） | 说明本技能只管辖四份文档，拒绝处理并说明理由 | 用户坚持时，记为「超出管辖范围」，不落笔、不汇报为待办 |
| 用户拒绝候选标题的反哺 | 该标题记为「不适用」，不写入模板 | 请用户给出归类后再决定是否反哺 |
| 项目文档与模板同一章节冲突 | 以项目现状为准修正项目文档，不反向改模板 | 无法判断孰是时，列候选问用户 |
| 模板存在但格式损坏或挖空点被误删 | 以技能自带模板为准补齐缺失的挖空点，保留项目值 | 无法判断以哪份为准时，列出差异问用户 |
| 四份文档已齐全时用户仍要求初始化 | 说明已齐全，改走「更新」并说明所选操作 | 用户坚持初始化时，按「更新」执行并在汇报中记录该分歧 |

## 执行纪律

- 动手前逐文档重新读取当前内容。项目文档可能已被并行会话或人工修改，会话早期读取的副本一律作废，凭旧副本断言「无变化」即错误；
- 一次调用只做一种操作；用户未点名操作时，按「有缺失文档 → 初始化缺失的，四份齐全 → 更新」判断，并说明所选操作；
- 用户只点名**管辖范围内**的部分文档时，只处理点名的那几份；点名范围外的文档按「异常与兜底」表拒绝并说明；
- 文档语言跟随项目主语言（默认中文）；
- 收尾汇报统一格式，逐文档列出：做了什么操作、动了哪些章节、遗留哪些待补充项、**未改动文件的核验输出**（`git status --porcelain <路径>` 为空；非 git 仓库则记录各文件大小与修改时间并声明局限）。
